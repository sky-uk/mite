Writing mite journeys and scenarios¶

Journeys¶

The basics of writing mite journey functions are explained in Your first scenario.

Data creation scenarios¶

For many workloads, it is necessary to populate a test environment with some data. For example, if we are performance testing a web appʼs signin, we need to seed the database with some usernames and passwords that we can use in our signin HTTP requests. In mite, this is accomplished by data creation scenarios.

Firstly, when running a data creation scenario, we need to activate miteʼs recorder component. This will write the data as it is created to a series of msgpack-format files in a directory called recorder_data. These files will become the input for a datapool for the load test journeys (see below).

Secondly, we need to write some journey functions that use the appʼs HTTP APIs to create data. An example might be as follows:

import uuid
from mite_http import mite_http

@mite_http
async def create_user(ctx):
    username = uuid.uuid4().hex
    async with ctx.transaction("Create user"):
        await ctx.http.post(ctx.config.get("app_url") + "/users/create",
                            json={"username": username, "password": "test1234"})
        await ctx.send("data_created", name="users", data={"username": username})

We use the python standard library uuid module to generate random user names, and create the users with a fixed password. We then send a message with the type data_created and the name users. This will be read by the recorder process, which listens to messages with type data_created. It will read the name of all such messages. For each message, the data is written as a msgpack dictionary into the file recorder_data/{name}.msgpack.

We create a scenario that runs this journey for a specific amount of time at a specific rate, which will generate our test users. If we have other types of data that need to be populated in the environment, we can write multiple journeys and run them as part of the same scenario. By giving a different name to each kind of data we create, we will get different output files for each type of data.

Note

The suggested approach to run the data creation journey for a specific time and TPS will generate an approximate number of test users. If precise control of the number of users generated is needed, you should instead use a (nonrecyclable) datapool as input to the creation scenario. The scenario will then be run once for each item in the data pool, creating a precisely specified number of users.

The next step is to create a data pool for the usernames:

import msgpack
from mite.datapools import RecyclableIterableDataPool

usernames = []
with open("recorder_data/users.msgpack", "rb") as handle:
    for msg in msgpack.Unpacker(handle, raw=False, use_list=False):
        usernames.append((msg["username"],))

usernames_datapool = RecyclableIterableDataPool(usernames)

Note

The datapool items (which are appended to the usernames variable) are tuples; this is required by miteʼs data pool framework.

Finally, we can use this datapool in our scenario:

@mite_http
async def signin(ctx, username):
    async with ctx.transaction("Log in"):
        await ctx.http.post(ctx.config.get("app_url") + "/login",
                            json={"username": username, "password": "test1234"})

def my_scenario():
    return [["my_file:signin", usernames_datapool, lambda start, end: 100]]

Constructing datapools¶

The example above builds a datapool by calling RecyclableIterableDataPool directly. Mite also provides decorator equivalents, which are usually tidier: the code that builds the data stays in its own function scope instead of leaving temporary variables lying around at module level.

import msgpack
from mite.datapools import recyclable_iterable_datapool

@recyclable_iterable_datapool
def usernames_datapool():
    usernames = []
    with open("recorder_data/users.msgpack", "rb") as handle:
        for msg in msgpack.Unpacker(handle, raw=False, use_list=False):
            usernames.append((msg["username"],))
    return usernames

The decorator calls the function immediately and replaces it with the resulting datapool, so usernames_datapool above is a RecyclableIterableDataPool instance, not a function. It can be passed to a scenario exactly like the directly-constructed pool.

Two kinds of pool are available, each with a class and a decorator form:

IterableDataPool / iterable_datapool

Hands out each item exactly once. Once the data is exhausted the pool raises DataPoolExhausted and the scenario stops. This is the “nonrecyclable” pool referred to above: use it when every item must be consumed exactly once, such as a data creation scenario that should run a precise number of times.

RecyclableIterableDataPool / recyclable_iterable_datapool

Items are returned to the pool when a journey checks them back in, so they are handed out again for the duration of the test. Use this for load test journeys that need to keep running for longer than the available data would otherwise allow.
